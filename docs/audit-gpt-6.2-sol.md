# Gavel's live moderation needs a safety pass

Do not demo or deploy a real one-press ban as “delete this message and restore the user with a swipe.” Telegram's documented behavior is wider and less reversible. The highest-impact fixes are to make the action match the display, require voice confirmation, and serialize actions and undo. Separately, the checkout's dates make the pre-hackathon disclosure a submission gate.

**Evidence.** I reviewed the contract, demo fixtures and copy, server and glasses sources, existing tests, manifests and lockfiles at `b9971e8`. Both typechecks passed; the existing suites passed **22 server / 13 glasses tests** in a scratch copy. The running service returned 200 for health, 401 for unpaired queue stats, and 200 for paired stats; the documented voice phrase parsed to a 1,440-minute mute without applying it. The top card was marked demo, stats stayed at 24 pending / 0 handled, and the simulator returned a 576×288 PNG. I didn't invoke seed, action, undo, or gesture endpoints, run attack traffic, or contact live Telegram, STT or LLM services. Below, Telegram semantics are documentation-backed; race consequences and provider-dependent behavior are static findings, not live reproductions.

## P0 · Clear eligibility before recording

**The repo already contains the complete baseline before the stated start.** Both author and committer dates are Nov 18, 2026, on all four commits, including `522d0e4` (application, Telegram backend and demo kit) and `b9971e8` (audit fixes). The required disclosure is still a TODO in `README.md:75–79` and `demo/SUBMISSION.md:27–28` points to it. If those dates reflect the actual work and Nov 23 is the official start, the baseline cannot be claimed as built during the event. **Fix:** preserve the history, confirm the actual event dates and reuse rules with the organizers, and disclose the baseline against concrete, eligible event-period commits. No unconditional technical P0 was verified.

## P1 · Fix before showing real moderation

1. **Ban has a larger blast radius than the card says, and undo doesn't restore membership.** `CONTRACT.md:24–26`, `README.md:18–22,59–63` and `demo/DEMO_SCRIPT.md:10–11` describe a message-scoped delete and show the user restored. `server/src/telegram.ts:14–19` invokes [banChatMember](https://core.telegram.org/bots/api/methods/banchatmember.md), whose message revocation Telegram documents as always true in supergroups/channels. [Unban](https://core.telegram.org/bots/api/methods/unbanchatmember.md) only lets the user rejoin. It neither rejoins them nor recovers history. The same “Banned” toast is used when a seeded card deliberately never touched Telegram (`server/src/service.ts:56–75`, `glasses/src/machine.ts:77–84,153–162`). **Fix:** make the single press a narrower action such as a short mute on supported chats; explicitly confirm a ban with its real scope. Label simulated receipts and use “Can rejoin; messages not restored” for real ban undo. Film that behavior, not the current storyboard claim.

2. **The displayed person can lag the actual ban target.** `glasses/src/main.ts:45–63,89–94,127–134` commits reducer state immediately but queues three asynchronous bridge writes. An incoming gesture can act on the new card ID while the previous sender's body is still visible, or while header and body reflect different cards. A bridge rejection also leaves the promise chain rejected and the optimistic render key set, stranding future renders. `glasses/src/machine.ts:93–112,142–150` makes the logical card actionable as soon as it loads. **Fix:** gate destructive gestures on a specific card revision after successful display acknowledgement, invalidate that revision during transition, coalesce paints and handle failure. Add a delayed-bridge test proving a gesture can't act on either card during a transition. Validate single/double sequencing with actual hardware: current tests submit these as isolated events (`glasses/src/machine.test.ts:40–49`), so they don't show whether a single can precede a double in a real callback stream.

3. **Voice does not do the confirmation the README promises.** `README.md:61` says confirmed voice commands. In practice, a keyword match is sufficient: `server/src/intent.ts:25–44` ignores negation, competing verbs and correction context, favoring a ban match; `glasses/src/main.ts:101–110` dispatches the parsed intent, and `glasses/src/machine.ts:202–209` immediately emits the action. “Heard” is not confirmation; the existing test asserts direct execution (`glasses/src/machine.test.ts:73–80`). **Fix:** treat STT as a draft. Accept only unambiguous commands with valid bounds, show action + exact target + scope on one screen, and require one tap to confirm or a swipe to cancel. Handle 422 in `glasses/src/api.ts:36–49,80–83` before the generic non-2xx throw so an unrecognized phrase says so.

4. **Concurrent decisions and undo are not tied to one authoritative outcome.** `server/src/service.ts:52–75` reads a pending card, awaits Telegram and only then resolves it without checking the resolve result. Two clients can act on the same card; an ignore can report success while a previously started ban is still going through. Distinct cards for the same user can also produce conflicting sanctions. An old undo token can reverse a newer sanction; a failed undo consumes the token before the Telegram call, and unmute writes a fixed permission set instead of restoring pre-existing per-member permissions (`server/src/service.ts:78–86`, `server/src/telegram.ts:22–38`). **Fix:** atomically claim a card before network I/O; serialize by chat + target, use idempotency keys and persist a sanction version. Capture prior restrictions; undo only the unsuperseded effect and preserve retryability on uncertain or transient errors. Use a deferred Telegram mock to verify duplicate requests, ignore vs. ban, and undo after a newer sanction.

5. **The pairing code is a global admin bearer, including the public demo default.** `server/src/index.ts:9–25,44` binds all interfaces and defaults to the documented demo code in development; production only checks that a value is nonempty, while `server/.env.example:1–4` supplies the same example. `server/src/app.ts:19–37` reflects arbitrary origins and has no rate limit or per-chat identity. Every paired client can read the shared queue and act on any returned item. `glasses/src/main.ts:15–26` accepts the bearer in a URL and persists it, and the default transport is HTTP. A different site doesn't automatically get the code or localStorage; that's not a CORS bypass. **Fix:** keep mock/seed mode isolated from any configured bot, require a high-entropy secret when Telegram is enabled, use HTTPS, rate limits and an allowed origin where compatible with Even Hub. Remove URL credentials; exchange a short-lived pairing code for revocable, individually scoped sessions. Limit the bot and queue to one configured test supergroup for the submission.

## P2 · Fix before expanding beyond one test supergroup

- **Telegram identity and group capabilities are not checked.** `server/src/index.ts:27–41` accepts non-private human text from any group and doesn't store chat type, role, or `sender_chat`. Named owners/admins can receive a ban affordance and remain at the front after a rejected action; I did not verify a successful ban of an admin. Telegram [Message](https://core.telegram.org/bots/api/types/message.md) says anonymous admin and channel-authored posts carry a distinct chat identity and may contain a fake user in `from`. The current bot filter can drop those posts; any surviving synthetic user is not a valid user-ban identity. Basic groups also cannot do [restrictChatMember](https://core.telegram.org/bots/api/methods/restrictchatmember.md), while the setup just says “test group” (`README.md:44–45`). **Fix:** require an allowlisted supergroup and check bot permissions at setup. Explicitly model user/chat senders, protect owners and admins using `getChatMember` before mutation, and leave chat-authored posts report-only in the hackathon build. [Channel bans](https://core.telegram.org/bots/api/methods/banchatsenderchat.md) have a broader scope than one human user.

- **Cards can represent content that no longer exists, or omit the content that needs review.** `server/src/index.ts:28–41` ignores edited messages, captions and Telegram text-link entities. `server/src/queue.ts:25–35` creates a new UUID for every add, even for the same chat/message. A benign post edited into a scam isn't reclassified, a corrected post keeps its old accusation, and duplicate deliveries aren't deduplicated. **Fix:** ingest eligible edits, text/caption and link entities; upsert by chat + message ID with a revision, discard stale refinements, and require the displayed revision on action (409 and refresh if stale).

- **Unvalidated action arguments and best-effort deletion misstate what happened.** Generic types do not validate JSON: `server/src/app.ts:32–34,39–47,54–73` validates the action name alone and assumes the shapes of skip and transcript inputs. `server/src/service.ts:57–69` coerces deletion counts through array slicing, forwards unchecked mute durations, always includes the flagged message in the selected deletion set, and discards every deletion failure. Telegram treats too-short or too-long restrictions as indefinite; [message deletion](https://core.telegram.org/bots/api/methods/deletemessage.md) has a 48-hour limit and rights constraints. “Last N” is only observed text since process start, may include messages posted after the flagged one, and can count an extra flagged message; the UI displays the requested number, not the actual number (`glasses/src/machine.ts:77–83`). **Fix:** Fastify runtime schemas with bounded integers, short strict audio and transcript limits, and explicit supported combinations. Define whether N includes the card. Compute the actual target set, avoid unbounded concurrent deletes, and report sanction and deletion outcomes separately (or disable bulk deletion for the demo).

- **Disk and uptime failures can desync Telegram and the queue.** `server/src/queue.ts:17–22,50–73` blindly loads JSON, mutates memory before saving, and replaces the file synchronously without an atomic write. A truncated file can stop startup. An I/O failure after a successful Telegram action can show 502, lose the pending card in memory, and omit the undo token; a restart can resurrect the old card (`server/src/app.ts:44–49`, `server/src/service.ts:62–75`). Undo tokens and observed history are volatile. **Fix:** use an atomic validated snapshot at minimum. Prefer a small SQLite action journal, with pending/applied/unknown outcomes and startup reconciliation. Test interrupted writes and restart during undo. Keep the database private and expire content, not just actions.

- **LLM output can override the shortlist and the reason shown on the glasses.** `server/src/llm.ts:27–51` sends raw member text as model input and averages the returned score equally with rules: a rules score of 0.10 can become 0.55, and 0.60 can drop to 0.30, below the `server/src/service.ts:35–39` flag threshold. The provider can also return arbitrary display text within the length cap. This is a prompt-injection exposure, not evidence that a particular live model will follow a member's instructions; the model does not itself call Telegram. Despite `README.md:73`, there is no test of `OpenAIRefiner` in the checked-in test suites. **Fix:** keep the demo rules-only; if refinement is enabled, preserve the rules shortlist, bound adjustments, use enumerated reason codes resolved locally, strip display controls and add mocked tests for untrusted/invalid outputs. Never use a model-proposed reason as authority for a sanction.

- **Provider slowness and queue growth can make the live demo stall.** `server/src/index.ts:27–41` awaits ingestion on grammY's sequential polling path, swallows handler errors and only serves an unconditional health check. `server/src/llm.ts:27–46` and `server/src/stt.ts:30–41` set no explicit deadline. `server/src/service.ts:19–33,74–81` caps IDs per user but not user keys or expired undo entries; `server/src/queue.ts:25–43,70–73` has no queue limit, sorts on reads and rewrites all pending items on every change. **Fix:** short downstream timeouts and a bounded/refillable LLM budget, visible Telegram readiness, bounded queue and observed-history retention, and actual pruning of expired tokens. Keep voice capture bounded too: `glasses/src/main.ts:98–104,127–130` collects chunks without a time cap or guaranteed stop and doesn't serialize start acknowledgement against release.

## P3 · Remove demo and handoff traps

- **First pairing stalls; the deployable build only knows localhost.** The `paired` event emits only `savePairing`; that effect creates a client and returns, never fetching. The only boot fetch has already run on an unpaired state (`glasses/src/machine.ts:124–129`, `glasses/src/main.ts:73–80,136–145`). Also the manifest only allows `http://localhost:8787` (`glasses/app.json:9–15`); in an actual Even App WebView, localhost is the phone, not the dev laptop, and changing the Vite URL alone doesn't update the whitelist ([Even Hub Networking](https://hub.evenrealities.com/docs/build/networking)). **Fix:** fetch and validate immediately after submit; offer retry/re-pair on 401; document or generate a matching HTTPS API origin and manifest entry. Treat the local simulator as evidence for neither first pairing nor on-device network setup. Promote the first pairing bug to P1 if judges must pair from a fresh install.

- **Skip and undo do not age out correctly on the client.** `glasses/src/machine.ts:111–115,152–187` accumulates duplicate skipped IDs after server wrap, keeps expired undo affordances, and accepts untagged toast timers from `glasses/src/main.ts:82–84` even if a later toast is showing. `glasses/src/api.ts:129–159` has different wrap and token behavior and a canned voice result. **Fix:** bound and reset skipped IDs on wrap, put an expiration on undo, tag timers by operation, and make mock and HTTP semantics match. Label mocked audio/action footage.

- **Privacy needs controls, but no member-controlled SSRF or committed provider key was found.** Outbound LLM/STT destinations are operator configured (`server/src/index.ts:12–17`), not derived from Telegram links. Keep provider destinations deployment-configured, validate their HTTPS origins, and avoid forwarding credentials to unapproved hosts. Queue/API rows include member text and identifiers (`server/src/types.ts:4–16`, `server/src/app.ts:32–35`); raw snippets and audio leave the machine with optional providers. Keep only synthetic or consented test data, use restrictive queue-file permissions and non-cacheable responses, and use reserved domains throughout seeds (`server/src/seed.ts:12–20` differs from the safer labelled eval fixtures). Only example env files are tracked; don't expose upstream raw error details to clients (`server/src/app.ts:48–49`).

**Recommended recording cut:** after resolving eligibility, pair from clean storage, post a synthetic human-authored scam into an allowlisted test supergroup, show the exact card that was acted on, and demonstrate a bounded mute and its actual undo with a non-admin test account. Show voice as a one-tap draft confirmation; label it simulated if STT isn't available. This preserves the 25% read/write story while making the 20% execution and 10% safety claims verifiable.
